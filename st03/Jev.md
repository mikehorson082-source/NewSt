# ТЗ v2.1: Jev-фильтр исполнения для тренд-оверлея

Sep 26, 2026 · @Tomas

## 1. Зачем этот слой и чем он не является

Jev — не генеративная модель и не источник торгового сигнала. Это **decision-модель**: на входе — состояние (state) и типизированный вопрос, на выходе — одно из трёх:

| Примитив   | Что возвращает                                                         | Где применяется в надстройке                              |
| ---------- | ---------------------------------------------------------------------- | --------------------------------------------------------- |
| **Noul**   | вероятность от 0 до 1, что утверждение истинно                         | риск-события: vol spike, разворот тренда, скачок фандинга |
| **Choice** | выбор одного варианта из заданного набора + распределение вероятностей | режим исполнения: normal / delayed / veto                 |
| **Score**  | уровень по упорядоченной шкале 2–10                                    | сила неблагоприятности окна исполнения                    |

Jev **не** заменяет сигнал \(F_t\), **не** меняет размер позиции вверх, **не** отменяет риск-лимиты и **не** предсказывает цену. Он может только:

- **сократить** целевую позицию;
- **отложить** исполнение;
- **отменить** ребаланс.

Это принципиально: любое суждение Jev может только **ухудшить** позицию относительно базового решения, но не улучшить её. Такая асимметрия защищает от случая, когда модель ошибается в свою пользу и увеличивает риск.

## 2. Архитектурное размещение

Jev встраивается в три точки `trend_overlay.py`, не требуя переписывания существующих функций:

| Точка               | Функция                                          | Что делает Jev                                                            | Что делает код                                      |
| ------------------- | ------------------------------------------------ | ------------------------------------------------------------------------- | --------------------------------------------------- |
| **A. Перед входом** | `rebalance()` после `enforce_limits()`           | оценивает вероятность неблагоприятного окна исполнения                    | применяет пороги, режет или пропускает              |
| **B. При срезке**   | `enforce_limits()` при выборе, какой лот срезать | даёт вероятность, что сокращение по инструменту \(i\) наименее болезненно | комбинирует с детерминированным вкладом в дисперсию |
| **C. В исполнении** | `backtest()` при `pending`/`due`                 | оценивает режим исполнения                                                | выбирает normal / delayed / veto                    |

Все три точки работают **параллельно** базовому контуру. Если Jev недоступен или его ответ не проходит калибровочный порог, система работает как раньше.

## 3. Контракт с Jev

### 3.1. State-объект

Перед каждым вопросом формируется компактный state из уже рассчитанных величин. Он не должен содержать ничего, что Jev не может обработать: **никаких сырых числовых рядов**, только агрегаты и метки.

```python
state = {
    "date": "2026-10-02",
    "ticker": "IMOEXF",
    "forecast_F": 1.12,
    "vol_ann": 0.22,
    "vol_ewma": 0.19,
    "vol_long": 0.25,
    "days_to_funding_high": 3,
    "funding_60d_mean": 0.0004,
    "funding_last": 0.0012,
    "spread_pct": 0.0008,
    "current_lots": 1,
    "target_lots": 2,
    "go_used_rub": 21400,
    "stress_rub": 48300,
    "mode": "normal",
}
```

### 3.2. Вопросы

Каждый вопрос — **атомарный**, с фиксированным горизонтом и измеримым событием. Формулировки не меняются между прогонами; изменение формулировки — новый эксперимент.

| ID  | Тип    | Формулировка                                                                                           | Горизонт  | Событие-метка                     |
| --- | ------ | ------------------------------------------------------------------------------------------------------ | --------- | --------------------------------- |
| Q1  | Noul   | «Вероятность, что реализованная волатильность по инструменту превысит 95-й процентиль годовой истории» | 5 сессий  | `vol_realized_5d > q95(vol_1y)`   |
| Q2  | Noul   | «Вероятность, что знак тренда по 63-дневному окну сменится»                                            | 10 сессий | `sign(z_63) != sign(z_63_prev)`   |
| Q3  | Noul   | «Вероятность, что фандинг за день превысит среднее за 60 дней вдвое»                                   | 3 сессии  | `funding > 2 × mean(funding_60d)` |
| Q4  | Choice | «Режим исполнения: normal / delayed / veto»                                                            | —         | выбирается кодом по порогам       |

### 3.3. Пороги и правила применения

Пороги фиксируются **до** бэктеста. Значения ниже — стартовые, не оптимум.

```python
# A. Перед входом
if kind == "open" and q1_p > 0.70:
    target = reduce(target, factor=0.5)   # сокращаем вдвое
if q4_choice == "veto" and q4_p > 0.65:
    skip_rebalance = True

# B. При срезке
for i in tickers_with_positions:
    score_i = contrib_i * (1 + p_jev_i)   # p_jev_i — вероятность, что срез болезненен
i = argmax(score_i)

# C. В исполнении
if q4_choice == "delayed" and q4_p > 0.60:
    due += 1                               # сдвигаем на одну сессию
```

Правило асимметрии: **ни одно из этих правил не может увеличить `target` или `|ideal|`**. Если Jev возвращает `normal`, исполнение идёт как раньше.

## 4. Калибровка: обязательное условие использования

Jev продаётся как калиброванная модель, но независимые аудиты показали расхождения. Прежде чем использовать пороги из раздела 3.3, необходимо проверить калибровку **на своих данных**.

### 4.1. Протокол калибровки

1. **Собрать метки.** Для каждого вопроса — история реализации события. Например, для Q1: `vol_realized_5d` по всем сессиям, `q95(vol_1y)` по скользящему окну. Метка — булево.

2. **Прогнать Jev на историческом state.** Каждый день — state из агрегатов на дату \(t\), вопрос, горизонт. Ответ — вероятность. Метка — реализация события на \(t + h\).

3. **Метрики калибровки:**

| Метрика                          | Что показывает                                               | Порог                       |
| -------------------------------- | ------------------------------------------------------------ | --------------------------- |
| ECE (Expected Calibration Error) | среднее расхождение между заявленной вероятностью и частотой | ≤ 0.05                      |
| Brier score                      | средняя квадратичная ошибка                                  | сравнить с базовой частотой |
| Reliability curve                | визуальная проверка по бинам                                 | монотонность                |
| Доля ответов > 0.9               | склонность к оверконфиденсу                                  | ≤ 20%                       |

4. **Если ECE > 0.05** — использовать **post-hoc калибровку** (temperature scaling) на калибровочном наборе из 100–500 примеров. После калибровки — повторная проверка ECE на отложенном наборе.

5. **Если и после калибровки ECE > 0.05** — Jev не используется для этого вопроса. Вопрос помечается как «некалибруемый на текущих данных».

### 4.2. Журнал суждений

Все ответы Jev сохраняются в отдельную таблицу. Без этого калибровку не проверить.

```sql
CREATE TABLE jev_judgments (
    id INTEGER PRIMARY KEY,
    date TEXT NOT NULL,
    ticker TEXT NOT NULL,
    question_id TEXT NOT NULL,     -- Q1, Q2, Q3, Q4
    question_type TEXT NOT NULL,   -- noul, choice, score
    state_json TEXT NOT NULL,
    p_jev REAL NOT NULL,
    chosen_option TEXT,            -- для choice
    confidence REAL,
    realized_event INTEGER,        -- NULL до наступления горизонта
    horizon_days INTEGER NOT NULL,
    created_at TEXT NOT NULL
);
```

`realized_event` заполняется **задним числом** после наступления горизонта. До заполнения — `NULL`. Если за 2 × horizon дней метка не появилась — вопрос помечается `stale`.

## 5. Изменения в бэктесте

### 5.1. Два параллельных прогона

Бэктест запускается **дважды** на одинаковых данных, с одинаковым лагом исполнения, с одинаковыми издержками:

| Прогон         | Что делает                          |
| -------------- | ----------------------------------- |
| **Baseline**   | `trend_overlay.backtest()` без Jev  |
| **Jev-фильтр** | тот же код + три точки из раздела 2 |

Сравнение — на одном и том же периоде, с одинаковой начальной стоимостью, с одинаковыми пополнениями (если есть).

### 5.2. Что мерить

Кроме метрик `summary()`, добавляются:

| Метрика                       | Что показывает                                                 |
| ----------------------------- | -------------------------------------------------------------- |
| Δ Sharpe (Jev − baseline)     | добавляет ли фильтр риск-скорректированную доходность          |
| Доля отменённых ребалансов    | как часто veto срабатывал                                      |
| Precision veto                | из отменённых — сколько были «правильными» (тренд развернулся) |
| Opportunity cost veto         | сколько доходности потеряно на отменённых                      |
| Δ порог безубыточных издержек | улучшает ли фильтр устойчивость к издержкам                    |
| Калибровка Q1–Q3              | ECE и Brier на отложенном периоде                              |

### 5.3. Критерии приёмки Jev-слоя

Jev-слой **признаётся полезным**, если выполнено всё:

- **Δ Sharpe ≥ +0.05** при издержках ×2 на отложенном периоде;
- **ECE ≤ 0.05** по каждому из Q1–Q3 после калибровки;
- **Precision veto ≥ 0.55** (отмены не хуже случайных);
- **Opportunity cost veto ≤ 30%** от дохода baseline на том же периоде;
- **Число ребалансов, где Jev изменил решение** — не более 25% от всех.

Если хотя бы один критерий не выполнен — Jev-слой **не включается** в боевой контур. Baseline остаётся.

## 6. Изменения в архитектуре и стеке

### 6.1. Новые модули

| `jev_filter.py`      | применение порогов в трёх точках                            | target, mode → adjusted target, mode        |

### 6.2. Изменения в существующих модулях

| Модуль             | Что меняется                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `trend_overlay.py` | `rebalance()` получает опциональный `jev_filter`; `enforce_limits()` — опциональный `jev_scorer`; `backtest()` — флаг `use_jev` |
| `state.db`         | новая таблица `jev_judgments`; в `orders_log` новое поле `jev_mode`                                                             |

| `ingest.py`        | без изменений                                                                                                                   |

### 6.3. Стек

- Python 3.12, `typesafe-sdk` (официальный SDK), `numpy`, `pandas`, `sqlite3`.
- API-ключ — в переменной окружения `TYPESAFE_API_KEY`, не в коде и не в репозитории.
- Fallback: если Jev недоступен (таймаут, ошибка API), система работает как baseline, в журнал пишется `jev_unavailable`.

## 7. Изменения в операционном регламенте

### 7.1. Ежедневный цикл

Добавляется шаг после расчёта лимитов:

| Когда                       | Система                                                                                                  | Вы  |
| --------------------------- | -------------------------------------------------------------------------------------------------------- | --- |
| Каждый торговый день, вечер | проверяет лимиты и **калибровку Jev** (ECE по накопленным меткам); если ECE > 0.05 — отдельное сообщение | —   |

Калибровка проверяется на **накопленных** метках, не на исторических. Первые 2–3 месяца меток мало, ECE нестабилен — это ожидаемо, не повод отключать фильтр.

### 7.2. Сообщение в Telegram

Пример с Jev:

```
Оверлей на 02.10.2026
• Продать 1 CNYRUBF: -2 → -3 (сигнал -0.68)
• Купить 1 IMOEXF: 0 → 1 (сигнал +1.12)
Jev: delayed (p=0.64) — исполнение во вторник
Риск ≈ 17 700 ₽/год · ГО ≈ 21 400 ₽ · стресс ≈ 48 300 ₽
[Исполнено] [Частично] [Пропустить]
```

Если Jev не сработал — строка отсутствует, сообщение как раньше.

### 7.3. Ручное вмешательство

Jev **не** отменяет необходимость ручного решения. Если вы видите `veto` и понимаете, что это ошибка (например, известное событие, которое Jev не учёл), вы можете исполнить вручную. Это фиксируется в журнале как `manual_override` с причиной.

## 8. Открытые вопросы к Jev

До этапа 3 (бэктест) нужно закрыть:

- [ ] **Доступ.** TypeSafe API напрямую или через OpenRouter? Локальная реализация (OpenJev, APUS) или облако?
- [ ] **Стоимость.** Цена за вызов при четырёх инструментах × три вопроса × 252 дня × 8 лет истории бэктеста.
- [ ] **Лимиты.** Rate limit, максимальный размер state, максимальное число опций в Choice.
- [ ] **Язык.** Jev лучше работает на английском. Формулировки вопросов — на английском, state — числовой.
- [ ] **Горизонт.** Jev не работает с датами как с упорядоченными значениями. Горизонт передаётся в тексте вопроса («in the next 5 trading sessions»), не как дата.
- [ ] **Воспроизводимость.** Детерминирован ли ответ при одинаковом state? Если нет — фиксировать seed или усреднять по N прогонам.

## 9. Что Jev не может и что с этим делать

Официально документированные ограничения, релевантные для надстройки:

| Ограничение                               | Последствие                             | Компенсация                                        |
| ----------------------------------------- | --------------------------------------- | -------------------------------------------------- |
| Не считает                                | нельзя просить «посчитай волатильность» | все числа — из кода, Jev получает готовые агрегаты |
| Не сравнивает даты                        | нельзя «сколько дней до экспирации»     | дни считает код, в state — целое число             |
| Оверконфиденс                             | может выдать p=0.99 на шум              | калибровка обязательна, пороги консервативные      |
| Не различает реальные и выдуманные данные | может «поверить» в некорректный state   | валидация state перед отправкой                    |
| Шум в большом state                       | качество падает на длинном контексте    | state ≤ 500 токенов, только агрегаты               |
| Не английский                             | точность ниже                           | вопросы и state — на английском                    |

## 11. Критерий запуска Jev-слоя

Фиксируется **до** первого прогона с Jev:

```python
def launch_decision_jev(delta_sharpe, ece_q1, ece_q2, ece_q3,
                        precision_veto, opp_cost_frac, changed_frac):
    checks = {
        "Δ Sharpe ≥ +0.05 при издержках ×2": delta_sharpe >= 0.05,
        "ECE Q1 ≤ 0.05": ece_q1 <= 0.05,
        "ECE Q2 ≤ 0.05": ece_q2 <= 0.05,
        "ECE Q3 ≤ 0.05": ece_q3 <= 0.05,
        "Precision veto ≥ 0.55": precision_veto >= 0.55,
        "Opportunity cost ≤ 30%": opp_cost_frac <= 0.30,
        "Доля изменённых ребалансов ≤ 25%": changed_frac <= 0.25,
    }
    checks["launch"] = all(checks.values())
    return checks
```

Не прошли — Jev-слой остаётся исследовательским, боевой контур работает на baseline.
